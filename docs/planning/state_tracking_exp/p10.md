# Part 10: New Conversations with "TGR + Tracker"

## Objective
Measure whether the tracker improves TGR in real conversations. We compare task success (pass^1), blocks,
violations and cost with frozen TGR and Direct, on the same tasks and settings.

## Why this part is needed
Parts 6–8 check saved steps only. When one decision changes, the rest of the conversation changes too: the agent
gets a different reply and does something else. Task success can only be measured by running the conversations
again.

## The guard: "TGR + tracker"
- **Base:** frozen TGR (rules from `from_shieldagent/rules/<domain>/`), with the same decision formula, ε = 0.1,
  all weights 1, and the same feedback.
- **The one change:** before the decision, the values of code-type predicates (Part 3) are replaced by the tracker
  values (Parts 4–5). The version for unknown values is the one chosen in Part 8.
- **Judge calls:**
  - the judge is called as in TGR, with the same prompt;
  - if every predicate of the tool is a code type, the judge is not called at all.
- **The state** is built from the live conversation the same way as in Part 4: database copy, replay of the
  executed calls, shown set and event log.

## Limits
- With 20 / 46 train tasks and 10 / 23 val tasks, and 3 trials each, pass^1 changes smaller than about 0.08 are
  hard to tell from noise.
- Most TGR blocks come from conversation predicates, which the tracker does not change. The gain may be small.
- The baselines were run earlier. The models are the same, but sampling has no seed, so some difference is noise.
- The guard reads the database, and frozen TGR and Direct do not. The report must say so.
