## Objective
A label for database facts that depends on no judge, no scorer and no person: τ-bench's own write tool, run on a
scratch copy of the state. It answers: "would the database accept this call, and if not, which check failed?"

## How it works
1. Deep-copy the state's database, and run the pending write call on the copy (`state.run_tool`). The real state is
   never touched.
2. Read the first `Error: ...` text, and map it to the fact it decides. The mapping is from table T3 of
   `output/logs/v3_wf_result_a.json`, with the critic's corrections. The 7 facts with a tool check:
   - the payment method differs from the original ↔ "the new payment method should be different from the current
     one";
   - the gift card covers the order total ↔ "insufficient gift card balance to pay for the order";
   - the replacements ↔ "<item> not found", "the number of items ... should match", "new item ... not found or
     available";
   - the gift card covers the price difference ↔ "insufficient gift card balance ..." (modify items, exchange);
   - the refund method ↔ "payment method should be either the original payment method or a gift card";
   - the booking's payment methods are in the profile ↔ "payment method ... not found" (book_reservation);
   - the passenger count is unchanged ↔ "number of passengers does not match".

   Plus the world part of two facts: "non-pending order" ↔ the order is pending; "non-delivered order" ↔ the order is
   delivered. `cancel_reservation` checks only "reservation not found".
3. The tools check in a fixed order. So a fact checked **after** the first failing check is "not decided by the
   tool". It is counted apart, never as agreement.
4. No error → every mapped fact is true. Exception: "different option", which the tool does not check.

Coverage: 7 database facts have a tool check. The others are labelled by the database field after exact replay.
That label is weak, because it reads the same database; it shows that the replay is right, not that the reading is.

## Steps
1. `state_tracker/v3/tool_check.py`: `check(state, call) -> {first_error, facts: {fact: True | False | None}}`.
2. Tests `tests/test_v3_tool_check.py`: one built case per Error text in the tool's order; the real state is
   unchanged after a call.
3. Run it on every saved write attempt of the development data (allowed, blocked and cap-override ones), and save
   the labels to `output/eval_v3/tool_labels.jsonl`. The audit (p4) and the fact check (p6) use them. The hold-out (the split
   of `fork/offline_v3.py`: the val conversations and the Stage B tries forked from them) gets its labels only in
   p12.

## How we know it is right, without a person
- It is the benchmark's own check, on an exact copy of the database (the replay was exact for 7,168 of 7,168 saved
  outputs).
- The tests cover every Error text, in the tool's own order.
- The real state is never changed (test).
