## Objective
Set by code every judge fact (or fact part) whose answer is plain in the text. And give the tiny questions (p8)
their code part: which messages to ask about.

## The pieces
1. **Message view** (`state_tracker/v3/message_view.py`):
   - user messages, agent text messages and tool outputs, in order, plus the pending call and the shown objects;
   - built from the executed history, **never cut at 24,000 characters**;
   - normalized text: accents removed, curly quotes made straight, markdown removed, lower case.
2. **Helpers:**
   - `user_typed(value)`: the value appears as a whole token in a user message. Order ids match with and without
     `#`; ZIP+4 matches the ZIP; six date formats;
   - `shown_forms(arg)`: an id and the ways it appears (product name and options; "PayPal", "gift card", last four
     digits; flight numbers);
   - `messages_naming(ids)`: the agent messages that name the call's ids. This is how code finds the listing for a
     tiny question, even when it came several turns earlier;
   - `reply_after(message)`: the user's next message;
   - `reply_is_no(text)`: strict (starts with no / not yet / wait / don't, and holds no yes / confirm / proceed).
3. **Info classes** (`state_tracker/v3/info_classes.py`): for each value in a text, where it comes from:
   - typed by the user;
   - a call argument;
   - a policy constant;
   - catalog data;
   - a database field of user U.

   The disclosure fact and the message builder (p10) use this one definition. The leak **checks** do not: they use a
   separate raw scan of the database (below), so they do not check themselves.
4. **`me`, the logged-in user:**
   - retail: the user id of the **first** successful `find_user_id_by_*` call;
   - airline: a user id the user typed, never the call's own arguments.
5. **Structure facts** (the first guess is about 12; p5 has the real list):
   - email / name + zip given by the user;
   - disclosure before login (the reply holds no database field the user did not type);
   - another user (the call's object belongs to someone other than `me`, from the database);
   - payment method chosen (the id or last four digits in the user's **latest** message about payment);
   - airline: ids established, booking information, passenger identity.
6. **Screens** (word lists, for example compensation words) only decide **whether to ask** a tiny question. A screen
   never sets a value alone. With no trigger word, the allowing value needs a code key too: the database owner check,
   and no other user's data in the reply.

## Steps

## How we know it is right, without a person
- **The view** equals the saved executed history on 100 % of development conversations.
- **Identity:**
  - retail: every identity value from the text, given to τ-bench's own `find_user_id_*` on the database copy,
    returns the task's user (critic check so far: 23 / 23 train, 91 / 91 Stage A);
  - airline (no login tool): the user id typed by the user exists in the database (`get_user_details` on the copy
    gives no Error), and equals the task's user in the task file.
- **Disclosure:** a token scan of each reply the fact lets through, **separate from the info classes**. Every string
  field of every user, order and payment record in the database is compared with the reply's tokens. 0 replies may
  hold a database value the user did not type.
- **Another user:** the owner of every call's object, from the database. 0 calls on another user's object are let
  through.
- **Screens:** 0 misses on the constructed sets. On a miss: fix the word list, then a second, fresh blind set
  (written by another separate agent) must pass.
- **Blocks added:** structure code looks at the **whole** conversation. For the core facts already tested by the
  critic (identity, disclosure), every block it adds where the judge allowed must have an objective reason
  (disclosure: the raw scan finds a database value the user did not type; identity: τ-bench's tool on the copy does
  not give the task's user), and the count against the judge is reported; a narrower window added 101 blocks in
  the critic's test. For the other structure facts (payment chosen, airline ids, booking information, passengers),
  every added block is labelled with τ-bench's tool and expected actions, and reported. The judge is not the truth.
