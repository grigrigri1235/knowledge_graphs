## Objective
Find the guard's wrong decisions by their **outcome**, locate the rule and facts behind each one, and blame a fact
definition or a rule only when fixing it improves the outcome. It runs first on the eval v2 data (frozen TGR and v2,
with the judge's saved values), on the development data only (p1 step 9), then again in p11 and p12 (p12 adds the
hold-out, once).

## Why it works this way
Checking a fact's value against the database is circular: that is what the tracker does. Only two checks are not
circular:
1. **τ-bench's own tool code** (p3): a second implementation of the same checks, written by τ-bench's authors. It
   finds bugs in our code, for the 7 facts it covers. It cannot tell whether a fact is *defined* right.
2. **The outcome:** τ-bench's expected actions and task success. The expected actions follow the policy, so a guard
   that blocks an expected action that never gets done is too strict somewhere.

Once facts are set by code, a wrong fact *definition* and a wrong *rule* are the same kind of error: the guard misreads
the policy. Both show up only in outcomes.

## Steps
1. **Find wrong decisions by outcome. Clear cases only; everything else is "unclear".**
   - **Too strict:** a block on an expected action (same tool, same arguments) that τ-bench's tool accepts, and that
     never runs later in the conversation.
   - **Code bug:** a database fact that disagrees with τ-bench's tool.
   - **Allowed but unwanted:** a write that is not an expected action and that the database accepted. This is
     reported, but **not** blamed on the guard: it can be the agent's own mistake that no rule covers.
2. **Locate:** for each wrong decision, the rule table (p2) gives the rule and the facts that tipped it. A saved
   "unknown" is looked up as its blocking value (`blocking_values`), and counted apart as "unknown-tipped".
3. **Blame by pattern:**
   - the same fact behind wrong decisions in several rules → that fact's definition is the suspect;
   - one rule wrong with several different facts → that rule is the suspect.
4. **Test each blame:** change the suspect (a new definition or rule file in `output/eval_v3/p4_variants/`, with its own sha256;
   a judge-set fact, which has no code definition yet, is tested by flipping its value with the rule table; the
   frozen files are
   untouched), re-run offline, and count:
   - the outcome-wrong decisions that go away;
   - the new ones that appear.

   **A blame counts only if the change removes wrong decisions and adds none** (pre-registered as P4.0 before p4
   runs). A rule blame is a finding only: v3 keeps the frozen rule set unless the user decides otherwise at the p4
   stop. It is checked again on the hold-out
   (p12).
5. **Report** `output/eval_v3/p4_audit.md`:
   - wrong decisions per data set, agent, rule, fact and length bin, with a few examples each, figures
     (`docs/reports/figures/v3_audit_*.png`) and the command that recomputes every number;
   - the suspects;
   - the tested blames.

   The result decides, with the user, the order of p5-p10.
6. **Pre-registration, part 2:** add the pass marks of p4-p12 to `output/eval_v3/preregistration.md`, and log the
   new sha256 **before any p5 output exists**. If the user changes p5-p10 at this stop, new marks may be added
   (logged); existing marks are never weakened. Then **STOP**: the user reads the audit and picks the order of p5-p10.
