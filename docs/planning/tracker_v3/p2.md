## Objective
For every rule, and every true/false combination of its facts, list which facts must change to satisfy it. This
table is used twice:
- by the block messages (p10): "this fact is not met; this makes it true";
- by the decision audit (p4): "these facts made the guard block".

## Why it is easy
The rules are small. Retail: 60 of 64 rules have one fact, 4 have two. Airline: 22 of 34 have one fact, 10 have two,
1 has three, and 1 has six (rule 25, cancellation). So a rule has at most 2^6 = 64 combinations.

## Steps
1. `state_tracker/v3/rule_table.py` reads `from_shieldagent/rules/<domain>/rule_set.json` (frozen, unchanged). For each
   rule:
   - parse the logic;
   - enumerate every true/false combination of its facts;
   - for each combination: does the rule hold? If not, list the **smallest sets of facts** that, flipped, make it
     hold.

   For example: `NOT gift card OR balance covers`, with gift card true and covers false, gives {covers} or
   {gift card}.
2. Write the table to `output/eval_v3/rule_table_<domain>.json`, with its sha256.
3. It is generic: no τ-bench names in the code, only the rule set's own fields. The same script runs on any TGR rule
   set.
4. Tests `tests/test_v3_rule_table.py`: hand-made rules (one fact, OR, AND, NOT, the 6-fact shape).

## New files
`state_tracker/v3/rule_table.py`, `output/eval_v3/rule_table_retail.json`, `rule_table_airline.json`,
`tests/test_v3_rule_table.py`, `scoring/v3_p2_rule_table_check.py`, `output/eval_v3/p2_rule_table.md`.

## How we know it is right, without a person
- **TGR's own decision code checks every row.** For each combination and each listed flip set, `mln.decide` is run on
  a check whose only rule is this one: with the combination it must block, and with the flips it must allow. 100 %.
- **No set is missing:** every flip set not listed must either fail to satisfy the rule, or contain a listed smaller
  set. Checked by brute force.
